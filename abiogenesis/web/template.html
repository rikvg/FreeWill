Replicators From Noise

Fill a computer's memory with random bytes. Let the bytes run as programs that can rewrite each other. With no fitness function and no goal, self-copying programs appear and take over. I rebuilt this experiment, tagged every byte with where it came from, and asked how the first replicator gets made: by luck, or by a process?

The setup

The language is BFF, a variant of Brainfuck from Agüera y Arcas et al. (2024). A program is 64 bytes. Code and data share the same tape, and two read/write heads can point anywhere in it. Only 10 of the 256 byte values do anything:

< >move head 0 left / right
{ }move head 1 left / right
+ -add / subtract 1 at head 0
.copy the byte at head 0 to head 1
,copy the byte at head 1 to head 0
[ ]loop while the byte at head 0 is not zero

The soup holds 131,072 random programs. Each epoch, every program is paired with a random partner. The two are joined into a 128-byte tape and run for up to 8,192 steps, so either can overwrite the other. Then they are split apart again. Each byte has a 1 in 4,096 chance of mutating per interaction. Nothing rewards copying. A program that happens to copy itself into its partner simply ends up with more copies of itself.

I wrote my own simulator in C, following the authors' reference code instruction for instruction, and added one thing: a provenance tag on every byte. It records when the byte's value was born, and how: part of the initial random soup, a mutation, or an edit by some program's +/-. Copy instructions carry tags along with values.

What took over

The most common replicator after takeover, with its essential bytes highlighted. Replacing any highlighted byte with an inert one destroys replication. Every other byte can be knocked out with no effect:

Three instructions matter: , } <. Inside a loop they mean: copy the byte at head 1 to head 0, move head 1 right, move head 0 left. The two heads walk in opposite directions, so the program copies itself into its neighbour backwards. A mirrored copy of [,}<] is ]<},[, which doesn't parse as a loop. So a working replicator needs the motif at both ends, mirrored. Its child is its mirror image, and its grandchild is itself again. The soup's second most common species is exactly the reverse of the first.

Copying is not enough

My ten-byte replicator passes the replication test, yet dropped into a soup it always dies out. The evolved one survives. The difference is what happens across a whole epoch. A replicator goes first half the time, keeping itself and writing a child into its partner. The other half it goes second, and the partner's code runs first. In 78% of those pairings that code runs on into the second half, moves the heads, and usually wrecks the replicator.
